# CursorLoom

**Early development preview — not a functional Synergy replacement.** CursorLoom is a work-in-progress local-network software KVM for macOS and Windows. Both platform implementations are incomplete; Windows has not been compiled or tested. Do not use for real remote control or sensitive input. Internal code names currently still use `InputBridge`.

## Plan
1. Define versioned interoperable messages and unit tests.
2. Build native macOS Swift app and Windows .NET app with explicit input permissions.
3. Add mutually authenticated encrypted transport, pairing, connection and disconnect safety.
4. Add input capture/injection, multi-monitor edge navigation, text clipboard, and configurable shortcuts.
5. Test across actual macOS and Windows devices; package installers.

Security: do not enable remote input or send clipboard/keystrokes over plaintext. Unintegrated macOS TLS 1.3 client and Windows TLS listener primitives require local identities and manually pinned peer certificates. They have not been tested together; pairing, certificate creation and authorization workflows are not implemented. The macOS library can import a user-provided PKCS#12 identity for a session; there is no UI for it yet. Each side verifies only the pinned certificate, not hostname or certificate validity, by design; pins must be verified out-of-band. The listener must not be used to control input until explicit consent and connection lifecycle safety are implemented. No production security or compatibility claims.

## Protocol draft
Transport will use TLS 1.3 with certificate pinning after explicit pairing. Application messages are UTF-8 JSON, one message per line, max 64 KiB, carrying `version`, `type`, and `payload`. Handshake and pairing details remain to be designed and tested. This format alone does not provide authentication or encryption.

Initial event types: `hello`, `pointer`, `button`, `key`, `scroll`, `clipboard`, `releaseAll`. Input keys use USB HID keyboard-page usage IDs, not platform-specific key codes. Validated input payloads: `key` = `{usage: integer 0..255, down: boolean}`; `pointer` = `{x: 0..1, y: 0..1}` in normalized primary-display coordinates; `button` = `{index: 0..1, down: boolean}` (left/right); `scroll` = `{vertical: integer -100..100, horizontal: integer -100..100}` in line units; `clipboard` = `{text: string}`, max 48,000 UTF-8 bytes; `releaseAll` = `{}`. Unknown fields are rejected. Binary content and file transfer are future work. These semantics are preliminary and have not undergone interoperability tests.

## Development status
macOS includes an initial SwiftUI status window and Accessibility permission prompt, plus protocol model and tests. Incremental bounded framing and input-message validation exist in Swift and C#; the C# code is not yet compiled or interoperability-tested. A standalone macOS input injection primitive and validated input commands are present but not connected to any UI or network. The primitive includes scrolling and opt-in text clipboard, supports only a subset of keys and primary-display mouse input, and has not been tested interactively. A passive opt-in macOS capture primitive now exists for primary-display mouse and some keyboard events; it is not attached to the UI or network, does not suppress local input, and requires real-device testing, including modifiers and permission revocation. Optional text clipboard monitors exist on both platforms; macOS has an isolated pasteboard test, while Windows has not been built or tested. They are not integrated into sessions. A preliminary Windows Forms status window and disconnected SendInput-based injection and passive low-level hook primitives exist but have not been compiled or tested. Windows capture does not suppress local input and is not connected to the app. A macOS sender and Windows receiver now exist as unconnected primitives, with bounded buffering and disconnect cleanup; they have not been compiled together or exercised over TLS. They are not attached to either UI. Consent/session state models exist for both platforms. A tested macOS coordinator guards forwarding and stops capture on failure. An experimental controller connects these primitives, but is not exposed in the UI and has not been tested against a real TLS peer. The Windows model is also not integrated; these components do not yet enforce runtime authorization in either app. End-to-end encrypted connection, mutual authentication, and input sharing are not integrated or tested.

Run initial macOS tests: `cd macos && swift test`. Run the preliminary window: `cd macos && swift run InputBridgeApp`. This development executable is not a packaged app; macOS permission behavior may vary when launched from a terminal.
Windows development preview requires Windows and the .NET 8 SDK: `dotnet run --project windows-app/InputBridge.Windows.csproj`. It is not verified yet, does not connect to another computer, and cannot control anything remotely.
